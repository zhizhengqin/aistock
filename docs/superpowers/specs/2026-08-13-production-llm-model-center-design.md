# 生产级大模型中心设计

日期：2026-08-13
状态：APPROVED
适用项目：睿见投研
适用分支：main

## 1. 背景与问题

睿见投研已经部署到京东云，生产环境由 API、worker、PostgreSQL、Redis 和 Nginx 多个容器组成。现有“大模型配置”仍是开发期实现：管理员保存后只修改 API 容器内存，worker 不会同步，容器重启后又恢复环境变量；未配置密钥时还会静默返回内置假报告。

这会产生五类生产风险：

1. 页面显示“已保存”，实际执行分析的 worker 仍使用旧模型。
2. 服务重启后配置丢失，管理员无法判断当前真正生效的模型。
3. 没有密钥或调用失败时可能生成看似真实的假报告。
4. 只能维护一个 DeepSeek 配置，无法测试并切换 DeepSeek、Kimi、通义千问。
5. “每日 Token 限额”只展示、不拦截，无法真正控制费用。

本次改造要把现有单模型表单升级为生产级模型中心。管理员可以保存多个真实模型、测试连接并安全切换默认模型；API 和 worker 使用同一份持久化配置；生产业务不再存在 Mock 模式或假 AI 报告。

## 2. 目标与非目标

### 2.1 本版目标

- 支持 DeepSeek、Kimi、通义千问三类供应商，并允许同一供应商保存多个模型。
- 统一使用 OpenAI 兼容的 Chat Completions 协议，保留现有轻量 `httpx` 调用方式。
- 支持新增、编辑、真实测试、设为默认、停用和软删除模型配置。
- 模型密钥加密落库，前端、日志和错误响应永远不暴露完整密钥。
- 默认模型写入 PostgreSQL，API 与 worker 共用，容器重启后不丢失。
- 一次分析任务从创建到完成锁定同一个模型配置。
- 删除生产业务 Mock；模型不可用时明确失败，不拼装残缺或伪造报告。
- 让每日 Token 限额成为跨容器、并发安全的真实费用保险丝。
- 用量记录可追溯到供应商、模型配置、任务和当次价格。
- 平滑迁移现有 `.env` 中的 DeepSeek 配置。
- 同步更新部署文档、架构说明、TODOS、用户使用手册和应用内使用指南。

### 2.2 本版不做

- 不引入 LangChain、LiteLLM 或独立模型网关。
- 不做自动故障转移。默认模型失败时必须显式报错，不能在用户不知情的情况下换模型。
- 不按不同业务模块分别指定模型；本版使用一个全局默认模型。
- 不做模型效果排行榜、自动评测平台或供应商账单对账。
- 不开放普通用户管理模型，所有配置操作仍仅限管理员。
- 不把模型 ID 做成固定下拉列表。供应商模型会持续更新，以真实测试结果作为准入条件。

## 3. 已确认的产品规则

1. 支持 DeepSeek、Kimi、通义千问。
2. 可以保存多个真实模型配置并随时测试。
3. 只有真实测试成功的配置才能设为默认。
4. 切换只影响新任务，正在执行的任务继续使用创建时锁定的模型。
5. 默认模型不能删除，必须先切换到另一个已测试模型。
6. 生产环境没有 Mock 开关；未配置或调用失败必须明确报错。
7. 自动化测试可以拦截外部 HTTP 请求，但测试假响应不得进入生产代码或用户报告。

## 4. 供应商兼容策略

三家供应商都支持 OpenAI 兼容的 `POST /chat/completions`、Bearer Token 鉴权和 JSON 输出模式，因此共用一个客户端抽象。

| 供应商 | 默认 Base URL | 示例模型 ID | JSON 输出 |
|---|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-v4-pro` | `response_format={"type":"json_object"}` |
| Kimi | `https://api.moonshot.cn/v1` | `kimi-k3` | `response_format={"type":"json_object"}` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` | `response_format={"type":"json_object"}` |

通义千问允许管理员把默认地址改成阿里云业务空间专属的公开 HTTPS 地址。客户端负责规范化尾部斜杠，并只追加一次 `/chat/completions`。

供应商差异集中放在适配器中：

- 共同参数：`model`、`messages`、`temperature`、`response_format`。
- 供应商专属参数采用明确白名单，不把某家参数透传给另一家。
- 结构化输出的提示词必须明确包含“JSON”和目标字段。
- 不允许模型工具调用，继续保持“数据由程序获取，模型只负责解读”的项目原则。

## 5. 数据模型

### 5.1 `llm_model_configs`：模型配置

| 字段 | 说明 |
|---|---|
| `id` | 应用侧预生成的 UUID 主键，供加密 AAD 和跨表追溯使用 |
| `provider` | `deepseek`、`kimi`、`qwen` |
| `display_name` | 管理员可读名称，例如“DeepSeek 主模型” |
| `model_name` | 供应商模型 ID |
| `base_url` | 规范化后的 API 根地址 |
| `encrypted_api_key` | 加密后的密钥正文 |
| `encryption_key_id`、`envelope_version`、`nonce` | 密钥信封元数据 |
| `credential_version` | 不可变随机版本；只有供应商 API Key 明文变化时创建新配置并生成新值 |
| `key_hint` | 仅用于展示的首尾脱敏提示，不可反推密钥 |
| `input_price_micro_yuan_per_million` | 每百万输入 Token 的价格快照；可为空 |
| `output_price_micro_yuan_per_million` | 每百万输出 Token 的价格快照；可为空 |
| `max_output_tokens` | 可选高级设置；为空时使用系统保守上限，真实请求始终发送硬限制 |
| `lifecycle_status` | `draft`、`active`、`disabled`、`retired`；删除另由 `deleted_at` 表示 |
| `supersedes_id` | 运行参数修改时指向上一版本，可为空 |
| `runtime_fingerprint` | 供应商、模型、地址、`credential_version` 和高级参数的稳定摘要；不包含主加密密钥 ID |
| `verified_test_id` | 当前指纹对应的成功能力测试；可为空 |
| `last_probe_status`、`last_probe_at`、`last_probe_latency_ms` | 最近人工探测展示状态，不决定默认模型是否可用 |
| `version` | 乐观并发整数版本 |
| `created_by` | 创建管理员 |
| `deleted_at` | 软删除时间 |
| `created_at`、`updated_at` | 审计时间 |

同一条配置通过 `version` 整数做乐观并发校验。所有修改请求携带 `expected_version`；不一致时返回 HTTP 409 和 `llm_config_conflict`。测试结束后如果运行参数指纹已经改变，测试结果不得用于切换，页面提示重新测试。

为保证任务锁定真正有效，已经成为默认模型或已被任务引用的运行参数版本不可原地修改。编辑供应商、模型 ID、Base URL、API Key 或最大输出 Token 时，系统创建一条关联旧版本的 `draft` 新版本；旧版本继续服务已创建任务。新版本测试并替代旧版本后，旧版本转为 `retired`，但仍可被历史任务读取。只修改显示名称或价格可以原地完成，并留下审计记录；每次调用仍保存当次价格快照。

状态机与操作严格分离：

- `draft -> active`：真实能力测试通过后激活，但不自动设为默认。
- `active -> disabled`：仅非默认配置可由管理员主动停用。
- `disabled -> active`：必须重新做停用后的真实能力测试；进入 `disabled` 时，原测试只保留审计用途，不再具备重新启用资格。
- `active -> retired`：只有同一配置链的新版本成功替代旧版本时发生，不提供人工恢复。启用非默认配置的新版本时可在同一事务退休旧版本；若旧版本是默认模型，则必须等新版本成功设为默认后再退休旧版本。切换到另一条无版本关系的模型不会退休原默认，只会取消其默认身份。
- 默认配置禁止停用和删除；软删除只允许 `draft`、`disabled` 或未被默认引用的 `retired`。
- `active` 表示可供新任务选择，`retired` 只允许历史任务读取，二者不能混用。

### 5.2 `llm_runtime_settings`：全局运行设置

表中固定保留一行：

| 字段 | 说明 |
|---|---|
| `id` | 固定为 1 |
| `default_model_config_id` | 当前默认模型外键，可为空 |
| `daily_token_limit` | 每日全局 Token 阈值，必须为正整数 |
| `switched_by` | 最后切换管理员 |
| `switched_at` | 最后切换时间 |
| `updated_at` | 设置更新时间 |

默认关系只保存在这一行，不在多条模型配置上维护多个 `is_default`，避免并发切换产生两个默认模型。

### 5.3 任务和用量追溯

`task_records` 增加可空字段 `llm_model_config_id`。所有需要调用大模型的任务在创建记录时解析并锁定不可变的模型运行参数版本；纯数据任务保持为空。

`llm_usage` 增加：

- `task_id`：关联任务，可为空。
- `llm_model_config_id`：关联模型配置，可为空以兼容旧记录。
- `provider_snapshot`、`model_snapshot`：历史显示不依赖当前配置名称。
- `input_price_snapshot`、`output_price_snapshot`：保存调用发生时每百万 Token 的 micro-yuan 单价。
- `cost_micro_yuan`：以百万分之一元保存费用，避免小额调用被整数“分”截断成零。
- `status`、`error_code`：成功与失败调用都可审计。

费用计算统一使用整数：`ceil(input_tokens × input_price_snapshot / 1,000,000) + ceil(output_tokens × output_price_snapshot / 1,000,000)`，结果为 micro-yuan；币种固定人民币。价格为空时成本也为空，页面显示“费用未配置”，不得当作零元。

定时系统任务允许 `user_id` 为空，不再用不存在的用户 ID `0` 记账。

### 5.4 测试、调用与额度账本

新增三类持久记录，避免把“最近一次探测”“一次业务调用”和“每日额度”混在模型配置或聚合表中：

1. `llm_model_test_runs`：保存配置 ID、运行参数指纹、管理员、用途（候选测试、激活测试、人工探测）、能力结果、耗时、脱敏错误、Token 和时间。配置上的 `verified_test_id` 只指向与当前运行参数指纹一致且成功的激活测试；单次人工探测失败只更新页面健康提示，不会隐式中断当前默认模型。
2. `llm_call_attempts`：每一次真实 HTTP 尝试一行，至少包含 `task_id`、稳定的 `step_key`、`attempt_no`、模型配置 ID、输入摘要、提示词版本、额度预留 ID、状态、响应摘要、Token、费用、`usage_source` 和时间；`task_id + step_key + attempt_no` 建唯一约束。测试、重试和 JSON 纠正都独立记账，不合并隐藏。每个成功业务步骤另持久化完整的已解析 JSON 结果、结果 Schema 版本和 SHA-256 完整性摘要；该内部步骤结果不作为用户可见的半成品报告。
3. `llm_token_reservations`：PostgreSQL 持久额度账本，保存唯一预留 ID、北京时间日期、预留量、结算量、状态和关联调用。Redis 只承担原子热计数，账本用于崩溃恢复与计数重建。

任务同时保存输入快照和 `prompt_version`。只有完整结构化结果与完整性摘要在同一数据库事务提交后，调用步骤才能标记为成功；worker 重启时校验摘要并复用完整结果。状态未知的步骤必须进入终态 `failed_unknown`，按保守额度结算、通知管理员并结束原任务，不无限保持处理中，也不自动重发。系统重试原任务始终使用创建时锁定的配置、输入和提示词版本；管理员“重新运行”必须创建新任务，并锁定当时默认模型。供应商调用无法保证 exactly-once，本系统只承诺本地可审计以及已确认成功且结果完整的步骤不会重复发起。

## 6. 密钥安全

新增生产环境密钥环，不复用 JWT 密钥。当前写密钥由 `LLM_CONFIG_ENCRYPTION_KEY_ID` 和对应密钥值指定，同时允许配置多个历史只读密钥。实现采用 `cryptography` 提供的 AES-GCM 认证加密，保证数据库泄露时 API Key 仍不可直接使用，并能检测密文篡改。

密文采用带版本信封：保存算法版本、`encryption_key_id`、随机生成且绝不复用的 96-bit nonce 和密文标签。AAD 精确定义为不可变字段 `envelope_version + config_uuid + provider`，不得包含乐观锁 `version`、显示名称、价格、`credential_version` 或主密钥 ID，防止密文跨记录替换且避免普通 PATCH 破坏解密。任何密文找不到对应 key ID 时，就绪检查失败。

规则如下：

- 生产环境缺少当前写密钥或历史配置所需读密钥时应用拒绝启动，并给出中文运维错误。
- 加密密钥只存在于京东云 `deploy/.env`，不提交 GitHub。
- PostgreSQL 备份与加密密钥必须分别备份；丢失加密密钥后，数据库中的模型密钥无法恢复。
- 前端列表和详情接口只返回 `key_hint`，从不返回密文或明文。
- 编辑时 API Key 留空表示保留原密钥；填写新值才重新加密。
- 日志、异常、测试结果和任务错误统一经过敏感信息清理。

主密钥轮换采用“双读单写”：先部署新写密钥并保留旧读密钥，分批重加密、完整校验后才能移除旧读密钥。主密钥重加密只改变信封密文、nonce 和 `encryption_key_id`，不得改变 `credential_version`、运行参数指纹、验证资格或生命周期。供应商 API Key 更新会创建不可变配置新版本和新的 `credential_version`；仍有排队或运行任务引用旧版本时，后台明确显示引用数量并提示暂缓吊销旧 Key。若管理员仍在供应商侧立即吊销，旧任务明确失败，不自动改用新模型；管理员可创建新任务重跑。

### 6.1 Base URL 安全

模型测试会由京东云服务器主动访问管理员填写的地址，因此必须防止它被用来探测服务器内网。

生产规则：

- 只允许 HTTPS、443 端口，不允许 URL 中包含用户名、密码、查询参数或 fragment。
- DeepSeek 与 Kimi 只允许各自官方域名。
- 通义千问允许 `dashscope.aliyuncs.com` 以及阿里云官方 `*.maas.aliyuncs.com`、`*.dashscope.aliyuncs.com` 域名。
- 使用唯一规范化实现处理 IDNA、大小写和尾点域名，并按域名标签边界匹配白名单；路径只允许供应商规定的 API 前缀。
- 拒绝 IP 字面量、localhost、环回、链路本地、私有网段，以及任一 A/AAAA 记录解析到上述地址的域名。
- 测试和每次业务调用都执行相同校验；连接阶段固定已校验目标或重新验证，防止 DNS 重绑定。
- URL 重定向和环境代理关闭；设置连接、读取、总时限与最大响应体。

未来如果确实要接自建私有网关，应另开受控配置项和专项安全评审，不通过当前页面直接放开任意地址。

## 7. 运行时解析与任务锁定

新增一个唯一的配置解析入口，返回不可变的 `LlmRuntimeConfig`：模型配置 ID、供应商、Base URL、解密后的密钥、模型 ID、价格和高级参数。

### 7.1 创建任务

所有需要 AI 的手动任务和定时任务执行相同步骤：

1. 开启数据库事务并锁定 `llm_runtime_settings` 固定行。
2. 查询全局默认模型，验证配置未删除、处于 `active` 状态，且 `verified_test_id` 与当前运行参数指纹一致。
3. 在同一事务写入任务、模型配置 ID、输入快照、提示词版本、扣减会员次数和事务 outbox 事件。
4. 提交后由 outbox 投递器把任务可靠投递给 worker；投递失败可重试，不重复建任务或扣次数。

如果没有可用默认模型，事务回滚，任务不创建、不扣会员次数，直接返回“尚未配置可用的大模型，请联系管理员”。默认切换取得同一行锁：任务事务先提交则锁定旧默认，切换事务先提交则其后的任务锁定新默认。这是“新任务”的唯一线性化定义。

### 7.2 执行任务

worker 根据任务记录中的模型配置 ID 加载精确配置，并把同一个 `LlmRuntimeConfig` 传给所有分析师、首席分析师和用量记录函数。运行过程中不再查询“当前默认模型”。被后续版本替代、停用或软删除的配置仍允许已有任务读取，但不能再创建新任务。每个分析步骤使用稳定 `step_key`；worker 重启后先读取调用尝试记录，已有完整成功结果则复用，不再次请求，未知状态按保守费用策略处理并进入可审计恢复流程。

这保证一次个股分析的五位分析师和最终汇总使用同一模型。管理员中途切换默认模型，只影响之后创建的任务。

### 7.3 无任务的调用

任何未来不经过任务系统的直接 AI 调用，必须在调用入口解析一次配置并显式传入，不允许 `chat()` 自己偷偷读取全局默认配置。这样调用者是否锁定模型在代码上是可见的。

## 8. 真实测试和安全切换

### 8.1 测试连接

测试使用管理员当前填写的候选配置向真实供应商发送低消耗请求。测试参数族必须与生产调用一致，并验证一份最小真实业务结构，而不是只验证鉴权或固定 `{"ok": true}`。成功必须同时满足：

- HTTP 请求成功。
- 返回结构中存在有效 `choices` 和 `usage`。
- 内容可解析为 JSON 对象。
- 响应模型信息存在，或由供应商适配器按明确契约完成等价校验。
- 当前模型支持 JSON mode、usage 返回和最大输出参数；能力结果写入测试记录。若不支持本版要求的 JSON mode，明确拒绝该模型，不静默退化成自由文本。

返回前端的数据包括测试状态、耗时、响应模型、能力结果和中文结果。每次测试写入 `llm_model_test_runs`，但不计入会员用量；真实 Token 仍计入系统每日限额和费用统计。单次人工探测失败只更新 `last_probe_status`，不会清空已验证资格或隐式停掉当前默认模型。

### 8.2 切换默认模型

“设为默认”不是单纯改数据库：

1. 读取候选配置及 `version`。
2. 进行一次新的真实测试，不复用旧测试结果。
3. 测试成功后开启数据库事务并锁定全局设置行。
4. 再次确认候选配置运行参数指纹未改变且未删除，保存本次成功测试为 `verified_test_id`；若为 `draft/disabled`，在同一事务转为 `active`。
5. 更新默认模型、切换人和切换时间；若它直接替代原默认的旧配置版本，同时把旧版本转为 `retired`。
6. 提交后返回新的默认配置。

任何一步失败都回滚并保留原默认模型。连续点击通过前后端双重防重处理。

## 9. 大模型客户端与错误处理

### 9.1 请求流程

1. 校验任务锁定配置与该模型已经验证的能力。
2. 创建持久额度预留和调用尝试记录，再通过 Redis Lua 原子预留 Token。
3. 使用统一客户端发送请求，并强制发送与预留一致的最大输出 Token 上限。
4. 校验 HTTP 响应和 JSON 业务结构。
5. 按真实 `usage` 原子结算；无 usage 或调用结果不确定时按预留上限保守结算。
6. 写入成功、失败或状态未知的调用尝试记录，并从尝试记录聚合 `llm_usage`。
7. 返回统一 `LLMResponse`。

### 9.2 重试规则

- 鉴权失败、模型不存在、参数错误不重试。
- 超时、HTTP 429、HTTP 5xx 最多重试两次，即最多三次请求，采用短指数退避。
- 返回内容不是合法 JSON 时，使用同一模型追加一次格式纠正请求；仍失败则任务失败。
- 每次重试与 JSON 纠正都是独立调用尝试，均受每日 Token 限额控制并分别记录实际或保守用量。

### 9.3 中文错误分类

| 内部错误码 | 用户提示 |
|---|---|
| `llm_not_configured` | 尚未配置可用的大模型，请联系管理员 |
| `llm_auth_failed` | 模型密钥无效，请管理员检查配置 |
| `llm_model_not_found` | 模型 ID 不存在或尚未开通 |
| `llm_quota_exceeded` | 模型供应商余额或调用额度不足 |
| `llm_daily_limit_reached` | 系统今日大模型用量已达上限 |
| `llm_rate_limited` | 模型服务繁忙，请稍后重试 |
| `llm_timeout` | 模型响应超时，请稍后重试 |
| `llm_invalid_json` | 模型返回格式异常，本次任务未生成报告 |
| `llm_unavailable` | 模型服务暂时不可用，请稍后重试 |

上游原始响应只写脱敏后的运维日志，不直接展示给普通用户。

### 9.4 任务完整性

现有多个 `_safe_chat()` 会吞掉异常并把 `{"error": ...}` 拼进报告，本次必须取消这种行为。

- 必要分析师任一失败，整项 AI 任务失败。
- 不保存半成品报告，不显示默认投资结论。
- 纯规则计算结果可以保留，但必须明确标记“规则判断”，不能冒充 AI 结论。
- 定时 AI 任务失败后复用现有管理员通知机制。

## 10. 每日 Token 保险丝

保险丝按北京时间自然日统计所有真实供应商调用，包括测试、重试、JSON 纠正、手动任务和定时任务。它是生产费用保护上限，不仅是展示统计。

### 10.1 并发安全算法

- 每次外部请求创建唯一额度预留 ID；PostgreSQL 账本先记录，Redis 同时维护北京时间日期对应的 `reserved` 与 `settled`。
- 输入预留不用经验字符比例，而使用适配器可证明不小于供应商计费用量的上界：完整序列化请求的 UTF-8 字节数，加上逐条消息封装、系统附加字段和供应商特殊 Token 的固定上界。适配器若不能给出经契约测试证明的输入上界，则该模型不能启用。
- 输出预留使用配置上限或系统保守上限；客户端必须向供应商发送一致的硬性输出 Token 限制。适配器必须确认该限制覆盖推理 Token 等全部计费输出；无法确认的模型不能启用。
- 通过 Redis Lua 脚本原子检查、预留和结算，阈值判断使用 `reserved + settled`。
- 请求成功后按供应商真实 `usage` 结算并释放多余预留。只有明确确认请求未发出时才能释放全部预留；超时、断连、进程崩溃或响应无 usage 时按预留上限保守结算，避免费用被记成零。
- 若供应商返回的真实总 Token 仍大于该次预留，视为保险丝不变量破坏：按真实量补记、立即锁停后续模型调用并通知管理员，必须修正适配器上界并人工解除后才能恢复。
- 达到阈值后拒绝新请求，已经发出的请求允许完成。
- Redis 开启 AOF、额度 Key 禁止淘汰。Redis 不可用、重启或当日 Key 丢失时生产环境失败关闭，先从 PostgreSQL 账本重建当日 `reserved/settled` 并核对后才恢复调用。
- 预留记录有状态和恢复租约。恢复任务处理进程崩溃留下的记录：有完整成功响应则结算真实量，结果未知则按预留上限结算，不把未知调用自动重发。

预留是费用保护，不是精确计费；精确统计以供应商实际返回的 Token 为准。

## 12. API 设计

所有端点继续位于 `/api/admin` 且要求管理员权限。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/llm-models` | 查询未删除模型和全局设置 |
| POST | `/llm-models/test` | 测试尚未保存的候选配置 |
| POST | `/llm-models` | 新增配置 |
| PATCH | `/llm-models/{id}` | 修改显示信息；运行参数变化时创建草稿新版本 |
| POST | `/llm-models/{id}/test` | 真实测试已保存配置，成功时记录当前指纹的验证资格 |
| POST | `/llm-models/{id}/enable` | 对草稿或停用配置执行新的真实测试，成功后启用为 `active` |
| POST | `/llm-models/{id}/disable` | 停用非默认配置 |
| POST | `/llm-models/{id}/activate` | 复测、确保为 `active` 并设为全局默认 |
| DELETE | `/llm-models/{id}` | 软删除非默认配置 |
| PATCH | `/llm-settings` | 修改每日 Token 限额 |
| GET | `/llm-usage` | 按模型和模块查询用量费用 |

删除旧的 `GET/PUT /admin/llm-config`。前端与测试同时迁移，不保留长期双接口。部署是单仓库整包升级，不需要为旧前端设置兼容期。

所有写接口校验空白字符、字段长度、供应商枚举、正整数限额、价格非负和 URL 安全规则。错误继续使用项目统一响应壳。

### 12.1 核心 API 契约

- 模型列表支持 `page`、`page_size`、`provider`、`lifecycle_status`，时间统一返回带时区 ISO 8601；Token 为 JSON 整数，单价和费用以 micro-yuan 整数返回，同时由前端格式化人民币。
- `POST /llm-models` 成功返回 HTTP 201、完整脱敏配置、`version=1` 和 `created_new_version=false`。
- `PATCH /llm-models/{id}` 请求携带 `expected_version`。只改显示名或价格时返回原 ID 和递增版本；运行参数变化时返回 HTTP 201、新配置 ID、`supersedes_id`、`created_new_version=true`。并发冲突返回 HTTP 409 / `llm_config_conflict`。
- 已保存配置的 PATCH 或测试中，`api_key` 省略或空字符串表示沿用该版本密钥；未保存候选 `POST /llm-models/test` 必须提供非空密钥。任何响应都只有 `key_hint`。
- `POST /llm-models/{id}/test` 返回 `test_run_id`、被测参数指纹、能力结果、耗时和错误；测试时运行参数被修改则结果保留审计但不授予验证资格，并返回 HTTP 409。
- `enable` 必须自己执行新的真实能力测试，或携带当前指纹一致、仍在有效期内的 `test_run_id`；对 `disabled` 配置，该测试必须晚于 `disabled_at`。服务端在同一事务再次校验测试时间、指纹、版本和状态后才能转为 `active`。`disable` 禁止操作默认配置；非法状态转换返回 HTTP 409 / `llm_invalid_state_transition`。
- `activate` 请求携带客户端生成的 `idempotency_key` 和 `expected_version`。服务端保存幂等结果；相同 key 重放返回同一响应，参数不同返回 HTTP 409。成功返回新默认配置和切换时间，失败不改变原默认。
- 删除成功返回 HTTP 204；默认模型返回 HTTP 409 / `llm_default_delete_forbidden`；仍被历史任务引用的配置只做软删除且继续允许旧任务读取。
- 统一错误响应至少包含 `code`、中文 `message`、可选 `field` 和 `request_id`；鉴权 401、权限 403、未找到 404、校验 422、并发或状态冲突 409、上游暂时不可用 503。
- 列表响应提供前端所需派生能力：`can_test`、`can_enable`、`can_disable`、`can_activate`、`can_delete`，但后端仍重复校验，不能信任按钮状态。

## 13. 旧配置迁移与部署

### 13.1 数据库迁移

Alembic 采用两阶段兼容迁移：第一阶段只增加新表、可空字段和索引，不删除旧字段或接口所需数据，保证短暂混合版本下旧 API/worker 与新代码都能运行；第二阶段必须等队列排空、所有容器升级且观察期通过后，才移除旧字段和旧接口。SQLite 只用于快速单元测试，所有锁、约束和迁移验收必须在与生产同主版本的 PostgreSQL 上完成。

### 13.2 首次引导

应用启动时，仅当数据库没有任何模型配置时执行一次旧配置迁移：

1. 读取 `DEEPSEEK_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL`、`DAILY_TOKEN_LIMIT`。
2. 使用当前写密钥 ID 对应的密钥信封加密 API Key。
3. 创建“DeepSeek 环境变量迁移”候选配置，暂不设为默认。
4. 启动引导程序发送一次低消耗真实测试。
5. 测试成功后在事务中标记成功并设为默认；测试失败则保留候选配置、保持“无默认模型”，写管理员通知并让部署就绪检查失败。

引导过程必须有并发保护，API 与 worker 同时启动也只能插入一次。数据库已有配置时，环境变量不得覆盖后台选择。

部署提供只读就绪命令，在 API 容器内检查“存在启用、未删除、测试成功的默认模型”，只返回状态和脱敏名称，不发起新的模型调用。GitHub Actions 在普通 `/api/health` 之后执行该命令；不满足条件时部署任务失败并保留清晰日志。

### 13.3 环境变量调整

- 新增并要求备份 `LLM_CONFIG_ENCRYPTION_KEY_ID`、当前写密钥值和历史只读密钥环；具体变量格式由工程计划确定，但必须支持双读单写。
- 删除 `LLM_MOCK`。
- `DEEPSEEK_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL` 仅作为旧配置首次引导和灾难恢复输入，文档标明弃用阶段。
- CI 删除 `LLM_MOCK=true`，改由测试夹具创建加密的测试配置并拦截供应商 HTTP。

### 13.4 上线顺序

1. 在京东云生成并分别备份当前写密钥与历史读密钥环。
2. 备份 PostgreSQL 和当前 `deploy/.env`，并使用脱敏生产快照预演 PostgreSQL upgrade、旧镜像兼容、downgrade 或 forward-fix。
3. 进入维护窗口，停止创建新 AI 任务，记录并排空 `pending/running` 队列；无法完成的旧任务明确标记失败并允许管理员上线后新建任务，禁止让缺少模型锁定字段的旧任务进入新 worker。
4. 执行第一阶段兼容迁移，先升级 worker 再升级 API；每一步验证旧新版本兼容和 outbox 消费。
5. 检查旧 DeepSeek 配置是否完成引导和部署就绪状态；引导测试失败时先修正，不允许带病恢复流量。
6. 恢复流量，在后台依次添加并真实测试 DeepSeek、Kimi、通义千问，选择默认模型。
7. 重启 API、worker 和 Redis，确认默认模型保持不变、额度可从账本重建。
8. 分别用三家模型生成一份真实小型分析作为生产验收。
9. 观察期通过且确认没有旧容器、旧队列和旧接口调用后，再单独执行第二阶段清理迁移。

应用尚未恢复对外写入时，可以回退兼容镜像并执行已验证的 Alembic downgrade。恢复写入后禁止用部署前数据库备份覆盖生产数据；故障优先通过兼容旧镜像或向前修复解决。数据库备份只用于灾难恢复并需要单独的数据差异处置。任何回滚都不得重新启用 Mock。

## 17. 已知风险与控制

| 风险 | 控制措施 |
|---|---|
| 切换时并发任务混用模型 | 任务创建时锁定模型配置 ID |
| 配置页被用于访问内网 | HTTPS 域名白名单、DNS 私网校验、禁重定向 |
| 数据库泄露模型密钥 | 独立密钥加密、密钥与数据库分离备份 |
| 加密密钥丢失 | 部署前强制独立备份并写入恢复手册 |
| 主密钥轮换导致旧配置不可解密 | 版本化信封、双读单写、分批重加密与就绪校验 |
| 供应商参数差异导致调用失败 | 单一协议加供应商适配器白名单 |
| 并发请求突破每日限额 | Redis 原子预留与实际用量校正 |
| worker 或 Redis 崩溃造成漏记/重复扣费 | PostgreSQL 额度账本、调用幂等记录、保守结算与计数重建 |
| 模型返回残缺 JSON | 同模型纠正一次，仍失败则整项任务失败 |
| 上线迁移导致现有 DeepSeek 中断 | 备份、一次性引导、真实测试、可回滚迁移 |
| 新旧容器或旧队列混跑 | 两阶段兼容迁移、维护窗口排空队列、事务 outbox |
